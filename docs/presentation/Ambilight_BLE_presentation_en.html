05 · BLE service map of the strip

One channel to write, one to reply

01 · FIND
FromBluetoothAddressAsync0x0865F0DE3701, up to 6 tries × 5 s
02 · HOLD
GattSessionMaintainConnection = true, wait for Connected, up to 6 × 2 s
03 · OPEN
GetGattServicesAsyncservice FFFF: write FF01, listen on FF02
04 · WRITE
FF01 no responseeach command renders instantly
05 · RESTORE
Drop → againa full connect cycle every ~6 s, indefinitely
Why no pairing: Windows PairAsync always returns Failed for this strip. It needs no pairing: the GATT characteristics are open, and pairing only breaks access.

10 · Brightness ladder

The bri byte is a percentage, not 0–255

The strip accepts values above 100 but distorts the colour. It is a firmware quirk, not LED physics. Ceiling: 100.

12 · Hang hunt · 02.11

Strip hang: four hypotheses

Symptom. At 50 ms, after 15–30 minutes the strip stops updating. The GUI tries to reconnect but cannot, and the strip is not on the air. Only a power-supply reset fixes it. The light does not go out: the strip holds its last colour.
radio: alive
1Rare deadlock of the strip BLE stack

The trigger is not the rate but duration or a combination of repeated frames and EMA transitions.

CHECKA 1–2 h run through the real GUI, v1.5 log
2Zombie link in the Windows stack

Only the laptop may have seen “not on the air”, while the strip could have been alive.

CHECKAt the moment of the hang, open Surplife: it sees the strip — a PC problem; it does not — firmware
3Power or overheating

Consistent with only a power reset helping.

CHECKReset and watch for when the hang returns
4Remote dynamic mode

Rainbow and chase override the static colour with their own algorithm.

CHECKSwitch the strip to static mode with the remote
Not the culprit: the write rate. lednotify soak 50 ms × 24.4 min, 24,000 commands at the same rate as the GUI: 0 failures, link alive, query after the run normal.
00 · Link drops · 08.11

101 drops: what the log showed

0

link drops since 02.11 per ambilight_log.txt. The strip vanishes for a second and returns on its own.

It is not the program that drops it. Writes went fine, then Windows itself sends ConnectionStatus → Disconnected.
Auto-reconnect works. The link returns within 1–6 s.
How long the link lived, log scale

Ruled out

  • Wi-Fi 5 GHz (channel 149) is not considered interference
  • Headphones were off, A2DP is not the cause

Suspected

  • Hung Windows BT stack after sleep
  • Power or reboot of the strip controller
  • Radio interference
  • Adapter power saving: Realtek 8852BE, Wi-Fi and BT on one chip, “allow the computer to turn off this device to save power” enabled
00 · Solution v1.9

We do not fix the drops, we make them invisible

How to tell the cause
1
Surplife on the phone during dropsStable: the PC or adapter is to blame. Drops too: the strip or its power is to blame.
2
Restart the BT adapter or rebootThe link lives for tens of minutes again: the stack after sleep is to blame.
3
Untick power savingOn the Realtek Bluetooth Adapter: “allow the computer to turn off this device to save power”.
Release v1.9, commit 889b533. Backup of the previous exe: AmbilightOT_v1.8_backup.exe. “NOT SEEN” on the air while the link is active is normal: BLE does not advertise while connected.
